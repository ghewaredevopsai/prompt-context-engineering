The six parts
of a prompt

Not a template to fill in. Six questions, each of which prevents one specific failure — so when an answer comes back wrong, you can name the part that was missing instead of rewording the whole thing and hoping.

The anatomy

Six parts, and the failure each one prevents

Context and examples are the wide ones — and they are the two people leave out, because they are the two that take effort. Role and format are a line each and get all the attention.

The widths are the point of the picture. A request is mostly context and examples by volume, which is why Tier 4 is about what goes in the window and Tier 2 is about the shape of what comes back. Role is the narrowest band and the one most blog posts are about.

The same job, twice

A one-liner is not a short prompt. It is five missing parts.

What people send

add a surcharge for oversized consignments

Every answer to this is a guess. The guesses are not random — they are the defaults of a million other codebases, which is exactly what you do not want.

The same request, assembled

# task
Add an oversize surcharge to rating.py.

# context
Rules are in docs/ops-runbook.md.
Money is integer paise.

# constraints
Do not change manifest.py.
No new dependencies. unittest only.

# format
The diff, then the test you added.
Notice what is not in the right-hand version: no "you are an expert Python developer", no "think step by step", no politeness. Every line either names a file, states a rule, or forbids something — and a reviewer could check any of them against the diff.

The test for a line in a prompt is the same as the test for a line in an instructions file: could a reviewer point at a diff and say it broke this? "Be careful with money" fails that test. "Money is integer paise" passes it.

Placement

Two of the six should never be typed twice

Retyping a constraint is a smell. If you have told it twice this week that money is integer paise, that line has stopped being part of your prompt and become part of your repository. How to write those files is the Copilot-as-Assistant module's Tier 3 — this module only says which parts belong there.

This slide is the boundary with the assistant module drawn rather than announced. We say which of the six parts should stop being typed; that module says which file to put it in and what the glob syntax is. If you are teaching both in one day, say that out loud here.

Read the answer

Which part was missing?

You asked for an oversize surcharge. You got this.

# rating.py
import decimal

def oversize_surcharge(consignment, rate=0.075):
    # 7.5% of declared value for oversize pieces
    if any(p.length_cm > 120 for p in consignment.parcels):
        return decimal.Decimal(consignment.declared_value_minor) * rate
    return decimal.Decimal(0)

"Added the surcharge as a percentage, seemed more flexible than a flat fee."

Name the part

  • It invented a percentage rule. The tariff says flat.
  • It added a dependency and returned a Decimal.
  • It read one dimension, not volume.

Three failures, two parts: context and constraints. Rewording the task would have fixed none of them.

Lab 1 now: send the one-liner, then send it assembled. Record turns to green and how many house rules each version broke. The number is the point, not the prose.

Worth saying plainly: the generated code is good code. It is readable, it is typed, it handles the empty case. It is also wrong in three ways that no amount of code-reading skill catches, because the rules it broke are not in the repository — they are in a runbook nobody attached.

Tier 3

The pattern set

Four moves that are worth knowing by name, what each one costs, and the one that most rooms are still using out of habit after the models stopped needing it.

4 slides · ~8 minutes Lab 3 follows · four patterns, one task Trainer: Rajesh Gheware

The four

Each one buys something. Each one is drawn as what it actually does.

Chain of thought is on the slide because the room will ask about it, and because a lot of internal prompt libraries still open with "think step by step". Against a reasoning model that is at best redundant and at worst it makes the model narrate its reasoning twice, once hidden and once out loud, and you are billed for both.

Choosing

When each one earns its tokens

PatternReach for it whenDo not bother whenCost
Few-shot The rule is easier to show than to say — naming conventions, a house error style, the shape of a good commit message. You can state the rule in one checkable line. Then state it. + the examples, every turn
Decomposition The change touches several files, or you want to review it in pieces rather than accept a 300-line diff on trust. The task is one function and one test. more turns, smaller each
Chain of thought You need the reasoning visible for a human to audit — a design decision someone will question next month. You are on a reasoning model and just want the answer. Set the effort instead. output tokens, the expensive kind
Self-critique The cost of a quiet defect is high: money, dates, boundaries, anything in a nightly job. You are going to read the diff carefully anyway, and it is ten lines. roughly double
None of these is a setting you leave on. A prompt file that always few-shots, always decomposes and always self-critiques costs four times the baseline on the day somebody asks it to rename a variable.

The last row of the cost column is the one to say out loud: self-critique roughly doubles the bill for the request. On a boundary bug in money code that is obviously worth it. On a docstring it is not, and the room should leave able to tell those apart without a table.

The move that is not on the list

Ask for the test first, and stop

Two requests, in this order

Write only the unittest for the
oversize surcharge, from the rules in
docs/ops-runbook.md. Do not write
the implementation. Stop after the test.

You review a test, not an implementation. A wrong test is obvious in a way that plausible code is not.

Why it beats every pattern above

It converts "is this right?" — which you have to be an expert to answer — into "does this run red, then green?", which anyone can answer.

It is also the cheapest thing on this deck: the test is short, and you stop paying the moment it is wrong.

How models differ
in habit

Not which is best — that is a different module, and the answer expires monthly. This is what actually varies between them when you hand the same request to each, and how to write a prompt that survives being run against a model you did not choose.

4 slides · ~10 minutes Not in the two-hour path Trainer: Rajesh Gheware

What varies

Six habits, and the one line of prompt that pins each one

HabitHow it shows upPin it with
Verbosity Two lines of code wrapped in six paragraphs, or a bare diff with no explanation at all. A format line. "The diff, then one sentence."
Willingness to ask Ambiguity met with a question, or with a confident guess that is never flagged as one. "If the rule is not in the files I gave you, stop and ask."
Scope discipline Touches only the file named, or tidies three neighbours while it is in there. An explicit do-not-touch list.
Instruction recall Holds a constraint for ten turns, or loses it after three. Restate the constraint in the turn that matters. Or start a new chat.
Tool-calling consistency Reads the two files you named, or opens nine and reads none properly. Name the files. Attachment beats search.
Refusal and hedging "I cannot be certain, but…" on something checkable, which reads as caution and costs you the answer. Give it the source of truth, then the hedge has nowhere to live.
Every pin in the right-hand column is a part of the prompt from Tier 1. That is the point of the tier: a well-assembled request is also the most portable one, because it leaves less for a habit to fill in.

Nothing on this slide names a model, and it should stay that way even when someone in the room asks directly. The honest answer is that the roster changes faster than this deck does, and that the six habits are stable while the rankings are not.

The ambiguity test

One under-specified request, three honest responses

The manifest total and the quote total disagree. Fix it.

Asks

"Two things disagree here. The runbook says fuel applies after surcharges; the notes file says base only. Which is authoritative?"

Best outcome, and the rarest.

Picks, and says so

"I have assumed the runbook is authoritative because it is dated later. If not, the change is one line."

Fine — the assumption is visible and cheap to reverse.

Picks, silently

Edits rating.py to match manifest.py, making both consistently wrong, and reports success.

The expensive one. Nothing in the diff says a decision was made.

You cannot change which of these you get by choosing a better model. You can change it by removing the ambiguity — attach the runbook, say which document wins — or by asking for the assumptions to be listed before the code.

This is the freight desk's real contradiction: ops-runbook.md and tariff-2026-notes.md disagree about whether fuel applies to surcharges, and manifest.py was written by somebody reading the wrong one. The third column is not hypothetical - it is what happens when nobody attaches either document.

Portability

Write for the model you will be moved to

Tuned to one model's habits

  • Relies on it asking when unsure
  • Relies on it holding a rule for ten turns
  • Relies on it not touching neighbouring files
  • "Think step by step" doing the work

Works beautifully until the seat is upgraded.

Portable

  • The rule is attached, not assumed
  • The constraint is restated where it matters
  • The do-not-touch list is explicit
  • The output has a shape a script checks

Survives a model change, a vendor change and a new joiner.

Extension lab: run one prompt against three models and write up what differed in habit, not in quality. Which column above did each one land in? That write-up is what to hand whoever picks the model — it is the input to the Token Optimization module, not a substitute for it.

The hand-off line matters: behaviour observations belong here, the selection decision belongs in the token module. A room that has had both should be able to say which evidence goes to which question.

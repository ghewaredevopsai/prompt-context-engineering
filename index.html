Prompt & Context Engineering

Two hours on the half of this craft that is not about any one vendor: what a request is made of, how to make an answer checkable, which named patterns are worth their tokens, what belongs in the context window, and how to notice when a prompt that used to work has stopped.

6 tiers · 6 labs · ~2 hours ~40% talk, ~60% hands-on Assumes: you write code for a living Trainer: Rajesh Gheware

The tiers

Each tier is a short talk and a lab. Take the ones you need — a room that only writes prompts for a chat window can stop after Tier 3; a room building a pipeline needs Tiers 2 and 5 most.

The labs

All six run against Meridian Freight Desk, a small fictional service whose house rules were never written down anywhere a program can read. Start at hands-on/.

LabWhat you doWhat you write down
0 Set the meter runningClone, run the tests, meter the repository Whole-repo estimate; which single file is a fifth of it
1 Rebuild the one-linerThe same request twice: bare, then assembled Turns to green, and house rules broken out of eight
2 Make it validateOne summary asked three ways, each run through a checker Contract pass rate over three runs, and output length
3 Four patterns, one taskIn pairs, two patterns each, then swap sheets Defects found against tokens spent, per pattern
4 Three groundingsOne question, three sizes of context Tokens sent, and whether it found the real defect
5 Break it, repair it, lock itBreak a working prompt three prescribed ways Violations before, broken and repaired; five checks
Measured, not scored. There is no pass mark and no total. Every lab asks for a number before and the same number after, and ends with a committed lab-N-record.md. Nobody grades your prompt — the sheet is what you take back to work.
Solutions ship with the module. solutions/ has a reference answer for every lab. Look whenever you want — nothing here is a spoiler, because nothing is scored.
One before-and-after is a data point, not a result. Where a lab measures something that varies between runs, the room puts its rows on the board and the spread across a dozen people is the finding. The labs say so where it matters.

What this module covers, and what it does not

In scope. The model-agnostic craft: what a request is made of, output contracts and validating a response, the named pattern set, grounding as a decision about how much and what kind, the failure taxonomy, drift, and evaluating a prompt repeatably.
Out of scope, deliberately. How to write the files — copilot-instructions.md, applyTo globs, prompt files, checking that an instruction file was used — belongs to the Copilot as Assistant module, Tier 3. Which model to choose, and what any of this costs in money, belongs to Token Optimization. Tool and MCP cost belongs to the MCP module. This module says which parts of a prompt should stop being typed; that module says which file to put them in.

The full list is in prompt-learning-outcomes.md, with where each outcome came from.
